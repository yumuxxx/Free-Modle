# 02 · 结构化提问与上下文管理

> 目标：问题变复杂时，知道怎么拆、怎么喂、怎么不跑偏。
> 前置：`tutorials/01`。
> 预计时间：1 天。

---

## 一、为什么需要"结构化"

单轮提问能覆盖的需求有限。一旦涉及下面任一条，就必须结构化：

- 需要多个步骤
- 需要你自己先判断/选择
- 输入材料很长
- 输出要分门别类
- 中间结果要复用

**核心思路：把一个大任务拆成 AI 能一口吃下的小任务，自己当调度者。**

---

## 二、三种拆分模式

### 模式 A：串行流水线

上一步的输出是下一步的输入。**每步可检查，错了不用从头来。**

```
原始材料 → [步骤1: 分类] → [步骤2: 分别处理] → [步骤3: 合并输出]
```

**适合**：内容生产、数据处理、格式转换。

**例子**：把 20 篇访谈记录 → 提取观点 → 按主题聚类 → 生成摘要报告。

**关键**：步骤 1 和 2 之间**必须人工检查**。这里是错误放大器——分错了类，后面全白做。

---

### 模式 B：分支探索

先让 AI 给几个方向，你选一个，再深入。

```
问题 → [让 AI 列 3 个方案] → 你选 → [展开所选方案] → 你验收 → [继续/换方案]
```

**适合**：方案设计、起名、架构选型、写作定调。

**关键**：**不要让它直接给最终答案**。先看选项，你的判断比它的默认选择更懂你的场景。

---

### 模式 C：迭代打磨

一个初始版本，反复修正。

```
v1 生成 → 你指出问题 → v2 → 再指出问题 → v3 ...
```

**适合**：润色、代码重构、设计稿。

**关键**：**每轮只改一类问题**。同时提 5 条修改意见，它会平均用力，每条都改得不到位。

---

## 三、上下文管理：喂什么，喂多少

### 3.1 上下文窗口的现实

标称 128K 上下文 ≠ 能用满 128K。三个问题：

1. **lost in the middle** —— 关键信息放在长文中段，容易被忽略。放开头或结尾
2. **成本线性增长** —— 每轮都把全部历史重发一遍，长会话第 10 轮比第 1 轮贵 10 倍
3. **注意力稀释** —— 塞入无关内容会拉低相关任务的表现

### 3.2 该喂什么

| 必喂 | 不该喂 |
|------|--------|
| 任务目标 | 整个代码库（只贴相关文件） |
| 约束条件 | 客套话和感谢 |
| 背景知识（它不可能知道的） | 重复出现的信息 |
| 输入材料 | 你自己还没想清楚的部分 |
| 输出验收标准 | 敏感信息 |

### 3.3 长材料处理策略

材料超过窗口，或不想浪费额度时：

**策略 1：先摘要，再提问**
```
第一轮：请把下面长文按原有结构压缩到 1/5，保留所有数字、结论、专有名词
第二轮：基于你的摘要，回答 <问题>
```
注意：摘要会丢细节。涉及精确数字的任务不要这么做。

**策略 2：分段 + 累加**
```
对每一段：请提取与 <主题> 相关的信息，无关的回复"无"
最后：把上面各段的提取结果合并，去重，按重要性排序
```

**策略 3：地图 + 定位**
```
第一轮：这份文档有哪些章节？每章用一句话概括
你：我要找 <内容>，可能在哪个章节？
它：第 3、7 章
你：请详细展开第 3 章中关于 <内容> 的部分
```
**这是最省额度的方式**，适合超长文档。

## 四、防止跑偏的技巧

### 4.1 每轮开始时重申目标

长会话中，AI 会逐渐"忘记"最初的要求。每 3–4 轮插入一句：

> "提醒一下，我们的目标是 <一句话>，当前在解决 <具体子问题>。"

### 4.2 让它复述需求

复杂任务开始前，先问：

> "在我开始之前，请用 3 句话复述你理解的任务目标、约束和验收标准。"

**看它的复述，比看它的结果更快发现问题。**

### 4.3 显式排除

AI 倾向于给你"全面的"答案，包含一堆你不要的。预先排除：

> "不要提 <X>。如果觉得 <X> 相关，只在最后用一行注明，不要展开。"

### 4.4 分段验收

不要等它做完 5 件事再一起检查。做一件，验收一件：

> "先只处理第 1 项，我确认后再继续。"

## 五、一个完整范例

**任务**：把公司内部的 30 条用户反馈整理成产品改进建议。

```markdown
## 第 1 轮：建立地图
下面有 30 条用户反馈。请先分类，只输出：
分类名 | 条数 | 涉及的主要功能模块
不要给任何建议，先让我确认分类是否合理。

<粘贴 30 条>

## 第 2 轮（你确认分类后）：逐类提取
针对"性能问题"这 5 条，请提取：
1. 用户遇到的具体现象（保留原话）
2. 出现的场景/条件
3. 用户建议的解决方向

## 第 3 轮：汇总
基于上面各类的分析，给出产品改进建议。
要求：
- 按影响面排序，不提影响面小的
- 每条建议注明依据来自哪几条反馈
- 标注哪些是用户明确提出的，哪些是你的推断
```

**为什么这么拆**：
- 第 1 轮你掌握了全局，且成本极低
- 第 2 轮分类处理，每类上下文干净，不受其他类干扰
- 第 3 轮只做综合，不让它边读材料边提建议（容易编）
