# 01 · 构建个人提示词工作流

> 目标：把"每次从零想提示词"变成"从自己的库里挑一个改"。
> 前置：读完 `tutorials/01` 和 `tutorials/02`。
> 预计时间：2–3 天（大部分时间花在整理你自己的历史对话上）。

---

## 为什么要建提示词库

同一个需求，你一周内可能遇到三次。每次重新措辞，结果质量还不稳定。

建库的三个好处：
1. **省时间** —— 不用从零组织语言
2. **质量稳** —— 经过验证的提示词，输出可预期
3. **能积累** —— 每次踩坑都变成库里的改进

---

## 第一步：盘点你的高频场景（半天）

**动作**：翻出过去一个月的 AI 对话记录，把每次对话用一句话归类。

常见归类：

| 类别 | 典型任务 |
|------|----------|
| 写 | 邮件、文档、周报、说明 |
| 读 | 总结、提取、翻译、对比 |
| 改 | 润色、缩写、改语气 |
| 审 | 代码审查、方案检查、错别字 |
| 学 | 解释概念、出练习、讲类比 |
| 想 | 头脑风暴、列方案、做决策辅助 |

**产出**：一张表，每行是"场景 + 出现频次"。**只给频次 ≥3 的场景建提示词**，低频的现场写更快。

---

## 第二步：为每个高频场景写 v1（1 天）

每个提示词按这个骨架写：

```markdown
## 场景：<一句话>

### 提示词
<完整提示词正文，用 <尖括号> 标出每次要替换的变量>

### 适用条件
<什么时候用这个>

### 输出验收
<怎么判断结果好不好>

### 已知问题
<这个提示词在什么情况下会失效>
```

### 一个真实例子

```markdown
## 场景：把口语化的会议记录整理成正式纪要

### 提示词
下面是我在会议中的速记，比较口语和零散。
请整理成正式会议纪要，要求：
1. 分三部分：决议事项、待办（含负责人和期限）、遗留问题
2. 待办必须表格化：事项 | 负责人 | 期限 | 依赖
3. 口语中的不确定表述（"可能""大概"）保留原意并标注 [待确认]
4. 不要添加速记中没有的信息
5. 200 字以内概述会议主题

速记内容：
<粘贴>

### 输出验收
- 待办表格能直接贴进项目管理工具
- 没有出现速记里没有的"决议"

### 已知问题
- 速记过于零散时会漏项，需人工核对
- 多人同时说话导致内容交错时，归属可能错
```

**注意最后两节**。它们是让提示词可维护的关键——没有"已知问题"的提示词，你下次用时会重复踩坑。

---

## 第三步：建立版本管理（半天）

提示词会演进。用最简单的文件名版本管理：

```
prompts/
  会议纪要-v3.md
  代码审查-v2.md
  README.md          # 索引：场景 → 当前版本 → 变更记录
```

`README.md` 里每个条目记三行：

```markdown
### 会议纪要
- 当前版本：v3
- v3 变更（2026-10-20）：增加 [待确认] 标注规则，避免把猜测当决议
- v2 变更（2026-10-12）：待办改为表格输出
```

**不要**用复杂工具。文件 + 命名就够，能 diff 就行。

---

## 第四步：每次使用后花 30 秒复盘

用完问自己一句：**"刚才哪个地方我手动改了？"**

- 改了一处 → 把改动写回提示词，版本 +1
- 改了很多处 → 说明场景拆分不够细，可能是两个场景混在一起了

这个习惯是提示词库能否变好的分水岭。不做复盘，库会停在 v1。

---

## 第五步：定期清理（每两周一次）

- **删**：连续两次使用都没手动改的提示词——说明要么场景没了，要么它已经够好
- **合并**：两个提示词 80% 相同的，合成一个带参数的
- **升级**：把"已知问题"里反复出现的问题，提到提示词正文里去预防

---

## 常见失败模式

| 现象 | 原因 | 解法 |
|------|------|------|
| 库建了很多但不用 | 场景选错，建的不是高频场景 | 回到第一步，用真实记录而不是想象 |
| 提示词越写越长 | 把所有例外情况都塞进去 | 拆成基础版 + 针对场景的补充说明 |
| 换模型后效果变差 | 提示词过度拟合某个模型的习惯 | 保留核心约束，删掉模型特定的技巧性描述 |
| 只有自己看得懂 | 缺少"适用条件" | 补上，假设三个月后的自己会忘 |
